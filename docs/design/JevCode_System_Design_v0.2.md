# JevCode System Design

**Version:** 0.2  
**Status:** 구현 범위를 축소한 설계 초안  
**Date:** 21 September 2026  
**Implementation:** TypeScript / Node.js, 단일 패키지  
**Initial platform:** Windows 11  
**Previous version:** [v0.1](JevCode_System_Design_v0.1.md)

## 1. 제품 방향

JevCode는 기존 코딩 에이전트를 실행하고, 실행 기록과 검증 결과를 한곳에서 확인하는 개인용 로컬 CLI다. Jev를 통한 자동 라우팅과 실행기 교체는 이 기반 위에서 효과를 검증할 후속 기능이다.

첫 버전의 성공 조건은 **Jev 없이도 기존 실행기를 직접 사용하는 것보다 작업 결과를 확인하고 실패를 추적하기 편리한가**이다. 자동 조율의 성공 조건은 별도로 측정한다.

기존 실행기의 읽기·수정·명령 실행·추론 루프는 유지한다. 런타임은 실행 전과 프로세스 종료 후에 개입한다. 모든 도구 호출에 모델 판단을 추가하지 않는다.

### 1.1 v0.1에서 조정한 사항

| 항목 | v0.2 방향 |
|---|---|
| MVP 범위 | Windows, 실행기 하나, 수동 실행, 기록, 취소, 검증 |
| Jev | MVP 의존성에서 제외, 후속 shadow 실험 |
| 세 실행기 지원 | 두 번째로 계약 검증 후 세 번째는 수요에 따라 추가 |
| 완료 판정 | 프로세스 종료·검증 통과·사용자 수락을 분리 |
| 권한 정책 | 어댑터가 실제 강제할 수 있는 범위만 보장 |
| 복구 | 기록 복구와 프로세스 재개를 분리; 자동 재실행 금지 |
| 기존 변경 | 초기 수정 작업은 깨끗한 작업 트리만 지원 |
| 구조 | 모노레포 대신 단일 패키지 내부 모듈 |
| 자동 인계 | 반복 실패 시의 후속 실험, 기본 경로에서 제외 |

### 1.2 설계 기본값

아래는 이번 개정의 권고 기본값이며 실제 환경을 검증한 결과는 아니다.

- Windows 11을 첫 지원 플랫폼으로 삼는다.
- 첫 어댑터 후보는 v0.1의 순서를 유지해 Claude Code로 둔다. 구현 전 호환성 검증을 통과해야 확정한다.
- 두 번째 후보는 Codex, 세 번째 후보는 Antigravity다. 기능 지원 여부는 설치 버전별로 검증한다.
- 실행마다 프로세스 하나를 생성하고 자동 retry·continue·switch는 하지 않는다.
- SQLite에 정규화된 실행 기록을 저장한다. 원시 스트림 보관은 기본 비활성화한다.
- 비용은 우선 관측 지표다. 초기 최적화 목표는 결과 확인 시간과 실패 추적 시간 감소다.

## 2. 범위와 출시 단계

| 단계 | 포함 | 합격 조건 |
|---|---|---|
| A: 호환성 검증 | 첫 실행기의 실행·권한·이벤트·종료 실험 | 제한을 강제하고 종료를 확인할 수 있는 버전/설정 확보 |
| B: 개인용 MVP | 한 실행기 수동 실행, 기록, 취소, 검증, inspect | 12절의 필수 시나리오 통과 |
| C: 공통 계약 검증 | 두 번째 실행기 | 컨트롤러에 실행기 이름별 분기 없이 같은 계약 통과 |
| D: Jev shadow | 라우팅·완료 권고 저장, 오프라인 비교 | 실행에 영향 없이 유효한 데이터 수집 |
| E: 보조 라우팅 | 사용자가 수락하는 추천 | 사전 정의한 비교 평가에서 효용 확인 |
| F: 선택적 확장 | 세 번째 실행기, 세션 재개, worktree, 인계 | 각 기능의 필요성과 별도 안전성 검증 |

MVP에는 auto 모드, 자동 완료 승인, 교차 실행기 인계, 병렬 실행, 자동 병합, 크로스 플랫폼 보장, 비용 최적화 라우터, 학습 기능을 넣지 않는다.

## 3. 아키텍처와 책임

```text
CLI
 └─ Runtime controller
     ├─ Workspace preflight / single-writer lock
     ├─ Executor adapter ── Native executor process
     ├─ Verification runner
     └─ SQLite event and result store

Later: stored bounded state ── Jev shadow evaluator ── decision records
```

| 구성요소 | 책임 |
|---|---|
| CLI | 사용자 입력, 진행 표시, 취소, 실행 결과 조회 |
| Controller | 상태 전이, 실행 예산, 잠금, 종료 확인 |
| Adapter | 버전별 실행 인자, capability 검사, 이벤트 변환, 프로세스 소유권 |
| Verification runner | 사전 승인된 검증 명령 실행 및 직접 관측 기록 |
| Store | 실행·시도·이벤트·검증·사용자 판정의 일관된 저장 |
| Jev (후속) | 제한된 입력에 대한 타입화된 의미 판단 |

프롬프트는 작업 목표를 전달한다. 권한 경계는 샌드박스나 실행기의 검증된 권한 기능으로 강제한다. 종료 코드와 파일 상태 같은 사실은 모델에 질의하지 않는다.

## 4. MVP 사용자 흐름

```text
jevcode init
jevcode doctor
jevcode run --agent claude "Fix the bounded bug"
jevcode inspect <run-id>
jevcode review <run-id> --accept
jevcode review <run-id> --reject
```

1. `init`에서 실행기, 작업 유형, 필수 검증 명령, 시간 제한을 설정한다.
2. `doctor`가 설치 버전과 지원 capability를 확인한다. 인증 여부를 부작용 없이 확인할 수 없다면 `unknown`으로 표시한다.
3. `run`이 작업 트리·잠금·권한·검증 설정을 확인하고 시작 스냅샷을 남긴다.
4. 실행기를 시작하고 stdout/stderr를 소비하면서 정규화된 이벤트를 저장한다.
5. 종료 또는 취소 후 프로세스 트리 종료를 확인한다.
6. 파일 변경 상태를 수집하고 필요한 검증을 수행한다.
7. 실행 결과, 검증 상태, 미확인 사항을 출력하고 종료한다. 사용자 판정을 기다리며 프로세스를 유지하지 않는다.
8. 사용자는 나중에 `review`로 수락 또는 거절을 기록할 수 있다. 이 명령은 코드를 수정하거나 커밋하지 않는다.

MVP의 `run`에는 기본 실행기 또는 명시적 선택만 존재한다. `--agent auto`와 `resume`은 구현 전까지 노출하지 않는다.

## 5. 권한과 지원 범위

### 5.1 capability 기반 실행 허용

어댑터는 OS·실행기 버전·적용 설정별로 다음을 보고한다. 값은 `verified`, `unsupported`, `unknown`이다.

- 비대화형 실행과 기계 판독 이벤트.
- 작업 트리 쓰기 제한과 추가 경로 접근 제한.
- 네트워크 제한.
- 미승인 명령 거부와 승인 거부 이벤트 관측.
- 프로세스 트리 종료 확인.
- 세션 식별자 및 재개 지원 (후속).

요청한 정책을 강제하는 데 필요한 capability가 `unknown` 또는 `unsupported`이면 시작을 차단한다. 프롬프트에 제한을 적었다는 이유로 capability를 지원한다고 표시하지 않는다.

샌드박스 경계, 실행기 자체 승인 정책, 런타임에서 관측만 가능한 사항을 `doctor`에 구분해 표시한다. 저장소 밖 접근의 기본 거부는 실행기 설치·인증에 필요한 명시적 경로 예외와 함께 설계한다.

### 5.2 MVP 승인 경로

MVP는 미리 설정된 범위에서 실행하고 추가 승인이 필요하면 거부 후 결과에 이유를 남긴다. 실행 중 승인 브로커와 승인 후 자동 재개는 후속 기능이다. 기존 사용자 승인 범위는 유지하되 범위를 넓히는 작업은 실행하지 않는다.

삭제 등 되돌리기 어려운 작업, push·배포·외부 메시지 전송은 초기 지원 범위에서 제외한다. 이를 차단할 수 없는 실행 설정으로는 수정 작업을 시작하지 않는다. 명령 문자열 블랙리스트만으로 임의 셸 명령의 효과를 분류할 수 있다고 가정하지 않는다.

검증 명령도 동일한 권한 제한과 프로세스 종료 제어를 받는다. 실행기가 제안한 명령이나 저장소 설정 변경을 자동 승인하지 않는다. 실행 시점의 승인된 설정 해시를 보관한다.

### 5.3 데이터 경계

환경 변수는 실행에 필요한 이름만 전달한다. 인증 저장소는 실행기 자체 방식으로 접근하며 자격증명을 복사하지 않는다. stdout/stderr에도 비밀이 포함될 수 있으므로 기본 기록은 필요한 필드만 추출하고 민감값을 제거한다. redaction의 완전성을 보장하지 않는다.

Jev shadow는 명시적으로 활성화하며 전송 대상 필드를 보여준다. 작업 요청, 제한된 diff 요약과 검증 결과만 보내고 전체 저장소와 원시 대화는 보내지 않는다.

## 6. 작업 트리와 실행 생명주기

### 6.1 작업 트리 기본 정책

수정 작업은 staged·unstaged·untracked 변경이 없는 작업 트리에서만 시작한다. 기존 변경이 있으면 변경 내용을 보존한 채 `BLOCKED`로 종료한다. 자동 stash, reset, clean은 하지 않는다. 사용자가 기존 변경을 정리한 뒤 새 실행을 시작할 수 있다.

읽기 전용 작업은 쓰기 차단이 검증된 실행 설정에서 기존 변경이 있어도 허용한다. ignored 파일도 비밀이나 중요 데이터일 수 있으므로 Git clean 상태를 전체 파일 안전성의 증거로 취급하지 않는다. `.git` 및 추가 보호 경로는 별도 제한한다.

시작 시 HEAD, index 상태, tracked 파일 상태와 untracked 목록, 정책/설정 해시를 기록한다. 종료 시 기준점 대비 변경을 계산한다. Git 상태만으로 ignored 파일의 복구를 보장하지 않는다.

잠금은 동일 작업 트리에 대한 JevCode 실행끼리의 동시 쓰기를 막는다. 경로 별칭과 대소문자를 정규화하고 Git 메타데이터 위치도 확인한다. 편집기나 외부 프로세스를 차단하지는 못한다. 실행 중 외부 수정이 의심되면 변경 소유권을 단정하지 않고 사용자 검토 대상으로 표시한다.

### 6.2 상태 모델

실행 상태와 결과 판정을 분리한다.

```text
CREATED -> PREFLIGHT -> RUNNING -> VERIFYING -> FINISHED
PREFLIGHT -> BLOCKED | FAILED | CANCELLING
RUNNING -> CANCELLING | RECOVERY_REQUIRED
VERIFYING -> CANCELLING | RECOVERY_REQUIRED
CANCELLING -> CANCELLED | RECOVERY_REQUIRED
```

실행기 실패도 종료가 확인되면 `VERIFYING`에서 변경 상태를 수집하고 `FINISHED`로 끝낸다. 성공을 의미하지 않는다. 상태별 허용 전이는 코드의 단일 전이표로 관리한다.

| 결과 필드 | 값 |
|---|---|
| executionOutcome | completed / failed / timed_out / cancelled / unknown |
| verificationStatus | passed / failed / skipped / unknown |
| acceptanceStatus | needs_review / accepted / rejected |

정상 종료와 필수 검증 통과만으로 사용자 요구가 충족되었다고 표시하지 않는다. MVP에서 의미적 수락은 사용자가 기록한다. 설명 작업처럼 검증 명령이 없는 경우 `skipped`와 이유를 남긴다.

### 6.3 취소와 재시작

- 실행 전 attempt 레코드를 생성하고 실행 후 프로세스 식별 정보를 즉시 저장한다.
- Windows에서는 Job Object 등 프로세스 트리 소유권과 종료 확인이 가능한 방식을 호환성 단계에서 검증한다. 구현 방식은 이 실험 결과로 선택한다.
- 취소 시 정상 종료를 요청하고 유예 시간 후 강제 종료한다. 검증 프로세스에도 같은 규칙을 적용한다.
- 자식 프로세스 종료를 확인하지 못하면 `RECOVERY_REQUIRED`로 남기고 새 writer를 허용하지 않는다.
- 재시작 시 미완료 실행은 복구 대상으로 분류한다. PID뿐 아니라 시작 시각과 소유권 증거를 확인해 PID 재사용을 구분한다.
- 확실하게 소유한 프로세스만 종료한다. 정체가 불명확하면 사용자에게 복구 이유를 표시하고 차단을 유지한다.
- 프로세스가 없음을 확인한 뒤 파일 상태를 재수집하고 `executionOutcome=unknown`인 중단 기록으로 종료한다. 새 작업은 별도 실행으로 시작한다.
- 살아 있는 실행기에 재접속하거나 작업을 자동 재실행하지 않는다. 기록 replay는 외부 명령을 실행하지 않는다.

## 7. 어댑터와 이벤트 계약

다음 코드는 핵심 관계를 설명하는 설계 스케치다. 전체 타입 구현은 호환성 실험 후 확정한다.

```typescript
interface ExecutorAdapter {
  readonly id: string;
  probe(): Promise<ExecutorHealth>;
  start(request: ExecutorRequest): Promise<ExecutorHandle>;
}

interface ExecutorHandle {
  attemptId: string;
  processIdentity: ProcessIdentity;
  events: AsyncIterable<ExecutorEvent>;
  exited: Promise<ExitResult>;
  cancel(): Promise<CancelResult>;
}

interface EventEnvelope {
  schemaVersion: number;
  runId: string;
  attemptId: string;
  sequence: number;
  at: string;
  source: "runtime" | "provider" | "user";
  type: string;
  payload: unknown;
  evidenceRef?: string;
}
```

`start` 실패 시 어댑터는 부분 생성된 프로세스를 정리한다. 정리가 불확실하면 복구에 필요한 식별 정보를 포함해 실패를 반환한다. 컨트롤러는 스트림 소비와 프로세스 종료를 함께 관찰한다. 스트림 종료를 프로세스 종료로 간주하지 않는다. 이벤트 큐는 크기를 제한하고 프로세스 출력이 막히지 않도록 지속적으로 소비한다.

주요 이벤트는 session_started, message_delta, tool_started, tool_finished, approval_denied, executor_claim, process_exited, workspace_observed, verification_result, parser_error다. 도구 이벤트에는 가능한 경우 provider tool-call ID를 보존한다.

실행기가 보고한 테스트 성공은 `source=provider`인 주장이다. 런타임이 직접 실행한 검증과 구분한다. 파일 변경 이벤트도 최종 diff의 대체물이 아니다.

알 수 없는 이벤트는 이름과 제한된 진단 정보를 남기고 계속 처리한다. 필수 종료 필드 누락이나 스트림 손상으로 결과를 신뢰할 수 없으면 프로세스를 정리하고 결과를 `unknown`으로 남긴다. stdout/stderr 수집 순서는 보존하되 두 스트림 사이의 실제 발생 순서를 보장한다고 주장하지 않는다.

## 8. 검증과 완료 판정

각 프로젝트는 실행 전에 필수 검증 명령을 설정한다. 명령은 executable·args·cwd로 분리하고 사용자 작업 문자열을 셸 코드로 연결하지 않는다. 셸이 꼭 필요한 명령은 승인된 고정 설정으로 취급한다.

검증 결과에는 command ID, 실행 명령, cwd, 시작·종료 시각, exit code, 상태, 실행 주체, 설정 해시, 검증 대상 상태 해시, 출력 요약과 증거 참조를 저장한다.

검증 순서는 다음과 같다.

1. 프로세스 트리 종료 확인.
2. 작업 트리 변경과 관측 가능한 정책 위반 확인.
3. 필수 검증 실행.
4. 검증 이후 파일 변경 재확인.
5. 실행·검증 결과와 미확인 사항 출력.

테스트가 코드를 수정하면 수정 전 상태에 대한 성공 결과를 최종 상태의 검증으로 쓰지 않는다. 추가 실행은 새 상태를 검증할 필요가 있을 때만 수행한다. 종료 코드 0, 빈 diff, 실행기의 완료 문구 각각은 의미적 성공의 충분조건이 아니다.

### 8.1 중복 검증 비용

MVP는 종료 후 필수 검증을 한 번 수행한다. 실행기에는 필요 시 targeted check를 하도록 요청하지만 실행기 주장만으로 필수 검증을 생략하지 않는다. 변경 작업이 이미 충족되어 diff가 없는 경우도 무조건 실패시키지 않고 검토 사유로 남긴다.

후속 최적화에서만 검증 재사용을 도입한다. 동일 명령, cwd, 설정, 관련 파일·의존성·환경이 같고 직접 관측한 기록일 때만 재사용한다. 외부 서비스에 의존하거나 관련 입력을 확정할 수 없는 검사는 캐시하지 않는다. 중복 실행 시간이 실제로 문제인지 먼저 측정한다.

## 9. 저장과 관측

SQLite를 실행 기록의 기준으로 사용한다. 상태 전이와 그 근거 이벤트는 같은 트랜잭션으로 기록하고 `(attemptId, sequence)`를 유일 키로 둔다. 이벤트 schema version과 어댑터 버전을 함께 저장한다.

| 레코드 | 핵심 내용 |
|---|---|
| runs | 작업, canonical workspace, 기준 Git 상태, 상태, 결과 필드 |
| attempts | 실행기/모델/설정/버전, 프로세스 identity, 세션 ID, 종료 결과 |
| events | sequence, source, type, 제한된 payload, evidence reference |
| verifications | 명령, 검증 상태, exit code, 대상 상태, 증거 |
| reviews | 사용자 수락/거절, 시각, 선택적 사유 |
| decisions (후속) | 전송 state, hash, 모델/질문/정책 버전, 응답, 적용 여부 |

원시 스트림은 사용자가 진단용으로 활성화한 경우에만 별도 파일로 저장한다. 임시 파일을 닫고 원자적으로 확정한 후 DB에서 참조한다. 크기를 제한하고 잘린 여부를 기록한다. 종료 시 압축은 선택 사항이며 실행 경로를 막지 않는다.

기본 보존안은 정규화 기록 30일, 진단 스트림 7일이다. 진행 중이거나 복구가 필요한 실행은 자동 정리하지 않는다. 만료 기록 정리는 명시적 유지관리 작업으로 제공한다. 보존값은 설정 가능하게 둔다.

저장 공간 부족이나 필수 기록 쓰기 실패 시 실행을 계속하며 관측 가능하다고 주장하지 않는다. 실행 중이면 취소를 시도하고 남은 복구 정보를 표시한다. 로그는 내보내기 전에 다시 민감정보 검사를 거친다.

MVP 지표는 실행 시간, 검증 시간, 런타임 자체 시간, 실패 이유, 취소 결과, 사용자 개입, 기록 조회의 유용성이다. 토큰/비용은 제공되는 경우에만 저장하며 누락값을 0으로 처리하지 않는다.

## 10. Jev 후속 실험

### 10.1 역할과 호출 예산

Jev는 생성 코드나 셸 명령을 반환하지 않는다. 작업 유형, 실행기 권고, 완료 여부에 대한 제한된 질문에 답한다. shadow 단계에서는 실행 전 라우팅 1회와 검증 후 완료 판단 1회 이내로 제한한다. timeout이나 잘못된 응답은 실험 실패로 기록하고 수동 실행 결과에 영향을 주지 않는다.

상태 입력에는 사용자 요청, 명시적 제약, 제한된 저장소 사실, 실행기 capability, 검증 결과와 출처, 제한된 diff 요약을 넣는다. 요구사항 목록이나 diff 요약을 실행기가 생성했다면 그 출처를 유지한다. 입력이 잘렸거나 근거가 부족하면 완료 판단을 `unknown`으로 할 수 있어야 한다.

Choice/Score의 confidence와 probabilities는 실제 응답 필드를 보존한다. Noul에는 이 필드를 요구하거나 인위적으로 생성하지 않는다. confidence를 실제 정답 확률로 해석하지 않는다. 완료 질문은 satisfied / unsatisfied / unknown으로 구성할 수 있다.

### 10.2 평가 방법

사용자 선택과의 일치율은 선호 지표로만 사용한다. 라우팅 효용은 별도 실행 비교로 평가한다.

- 동일한 초기 저장소 snapshot과 동일한 작업·검증 조건을 준비한다.
- 고정 실행기, 단순 규칙 라우터, Jev 라우터를 비교한다.
- 작업 유형별로 결과를 나누고 모델·실행기 버전, 예산과 실행 순서를 기록한다.
- 가능한 범위에서 실행 순서를 무작위화하고 반복 실행으로 변동성을 확인한다.
- 사용자 수락과 사전에 정의한 acceptance check를 함께 사용한다. 라우터 자신의 판정을 정답 라벨로 쓰지 않는다.
- 튜닝 작업과 최종 평가 작업을 분리한다. 기록 replay만으로 선택하지 않은 실행기의 성능을 알 수 있다고 주장하지 않는다.

20~50개 작업은 파서·질문·평가 절차의 결함 탐색용이다. 자동화 안전성을 입증하는 표본으로 취급하지 않는다.

### 10.3 승격과 중단 기준

보조 라우팅 평가 전에 평가 계획에 다음 값을 고정한다: 포함할 작업 유형, 유형별 표본 수, 허용 성공률 저하, 필요한 시간 또는 비용 개선폭, 불확실성 계산 방식, 실험 예산. 이 값이 비어 있으면 shadow에서 승격하지 않는다.

품질 하한을 만족하면서 시간·비용·사용자 개입 중 사전 선택한 목표가 개선되어야 보조 추천을 출시한다. 차이가 불명확하거나 단순 규칙이 비슷한 성능이면 기본 실행기/규칙을 유지한다. 낮은 confidence만으로 반복 호출하거나 자동으로 계속 작업하지 않는다.

자동 완료 판정과 자동 인계는 보조 라우팅 승격에 포함되지 않는다. 각각 별도 false-finish 허용치와 실패 복구 평가가 필요하다. 근거가 없으면 사용자의 수락 흐름을 유지한다.

## 11. 후속 인계와 세션 재개

같은 실행기 재개와 다른 실행기 인계를 구분한다. 재개는 provider session ID, 작업 트리 기준점, 모델·정책 호환성을 확인한 뒤 사용자 요청으로 새 attempt를 만든다. 기존 attempt를 이어 쓴 것으로 기록하지 않는다.

인계는 반복 실패나 사용자의 명시적 요청이 있을 때 검토한다. 이전 프로세스가 완전히 종료된 뒤 작업 목표, 제약, 기준 diff, 시도한 접근, 직접 검증과 실행기 주장, 미해결 사항을 전달한다. 전체 대화를 복사하지 않는다.

새 실행기의 저장소 재탐색 시간과 토큰도 인계 비용에 포함한다. 총 시도 수와 총 시간 예산을 공유하며 계속/교체를 무한 반복하지 않는다.

Worktree는 추후 격리 기능이다. dirty tree 전달, ignored 파일, 공유 Git 메타데이터, 외부 서비스 부작용을 별도로 다룬다. Worktree만으로 임의 명령을 안전하게 실행할 수 있다고 간주하지 않는다. 자동 병합은 지원 범위에 넣지 않는다.

## 12. 구현 순서와 검증 기준

### A. 호환성 검증부터 시작

지원 후보 버전을 고정하고 실제 작은 테스트 저장소에서 다음을 확인한다: 읽기 작업, 제한된 수정, 승인 거부, 작업 트리 밖 접근 거부, stdout/stderr 처리, 정상 종료, 장시간 명령 취소, 자식 프로세스 종료. 결과를 fixture와 capability 보고서로 남긴다.

필수 권한이나 종료 보장이 확보되지 않으면 CLI 구현 범위를 줄이거나 SDK/격리 실행 방식을 조사한다. 검증되지 않은 지원을 전제로 나머지 런타임을 만들지 않는다.

### B. MVP 구현

단일 패키지에 CLI, controller, adapter 하나, verification, storage를 구현한다. Mock executor로 실패 경로를 먼저 재현하고 실제 실행기로 계약을 확인한다.

필수 합격 시나리오:

1. 변경 없는 설명 작업: 정상 종료와 검증 생략, 사용자 검토 필요를 구분한다.
2. 제한된 수정 작업: 변경 파일과 필수 검증 결과를 기록한다.
3. 실행기는 완료를 주장하지만 테스트 실패: 검증 실패로 표시한다.
4. 승인 거부 후 종료 코드 0: 작업 성공으로 오인하지 않는다.
5. malformed JSON 또는 종료 이벤트 누락: 불명확한 결과를 성공 처리하지 않는다.
6. 취소/timeout: 실행기와 자식 프로세스가 종료되고 변경이 보존된다.
7. dirty tree: 수정 실행을 차단하고 기존 staged·unstaged·untracked 내용을 그대로 둔다.
8. controller 강제 종료: 재시작 후 중복 실행을 막고 복구 상태를 보여준다.
9. 두 JevCode 동시 실행: 같은 작업 트리의 writer는 하나만 허용한다.
10. 검증 명령 timeout/실패: 검증 프로세스를 정리하고 실행 결과와 분리한다.
11. 이벤트 저장 중 중단/실패: 불완전 기록을 감지하고 성공으로 복구하지 않는다.
12. Jev 설정과 네트워크 연결 없이 수동 실행·inspect·review가 동작한다.

통과 후 대표 개인 작업에서 직접 CLI 사용 대비 확인·추적에 도움이 되는지 기록한다. 단순한 실행 감싸기에 그쳐 불편만 늘면 기능 확장 전에 흐름을 수정한다.

### C 이후

두 번째 어댑터로 공통 계약을 검증한다. 그 뒤 Jev shadow와 비교 평가를 진행한다. 세 번째 어댑터와 다른 OS는 실제 수요와 유지보수 예산이 있을 때 추가한다.

## 15. 참고와 근거의 범위

이 문서는 제품 범위와 구현 계약의 개정안이며 실행 가능한 구현이나 설치 환경 검증 보고서가 아니다. 실행 인자는 본문에 고정하지 않고 어댑터 호환성 보고서에서 버전별로 관리한다.

- [TypeSafe Quick start](https://docs.typesafe.ai/introduction/quickstart): Choice, Score, Noul 응답 구조.
- [TypeSafe Confidence](https://docs.typesafe.ai/confidence): confidence와 응답 분포의 관계; Noul의 차이.
- [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference): print 모드 권한 요청 처리와 버전 조건.
- [Antigravity headless mode](https://antigravity.google/docs/cli/headless/): 비대화형 실행과 승인 거부 후 정상 종료 가능성.

위 문서들은 v0.1 평가 과정에서 확인한 참고 자료다. 모든 실행기의 최신 기능을 이번 개정에서 다시 검증했다는 의미는 아니다. 실제 지원 선언은 단계 A와 각 후속 어댑터의 계약 테스트 결과를 따른다.
