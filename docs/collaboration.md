## 한 줄

**사용자와 Claude가 대화로 설계하고 명령을 쓰면, jevcode가 Codex 에이전트를 격리해서 돌리고, 사람이 근거를 보고 판정한다.** 판정 기록은 판단 모델(Jev)을 평가하는 정답 데이터로도 쌓인다.

## 누가 무엇을 하나

| 참여자 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 사용자 | 게임 방향과 설계 결정, run 실행, Play, **판정(수락·거절)**, 커밋·푸시 | - |
| Claude(이 대화) | 설계 정리와 문서 기록, run 명령 작성(`docs/runs/<id>.md`), 명령을 코드와 대조, 리뷰 근거 모으기(시뮬레이터 실행, diff 읽기), jevcode 도구 개선 | 게임 코드를 직접 고치지 않는다(코드는 run으로만 바뀐다). 판정을 대신하지 않는다 |
| Codex 에이전트(jevcode run) | 명령대로 `src/Core`, `src/Core.Sim`, Unity 코드와 테스트를 바꾸고, 마지막 메시지에 검증 근거를 남긴다 | `.git` 쓰기, 커밋, 범위 밖 수정 |
| jevcode | 격리 실행, 스냅숏·diff 기록, 검증(dotnet test, Unity 재컴파일), 리뷰 화면, shadow 판단(Jev, rules) 기록 | 판정 |

## 한 사이클

```
1. 설계 대화         Play 피드백이나 문제를 이야기하고 방향을 정한다
2. 설계 기록         behind-the-curtain/docs/ai-design.md (정한 것, 단계 표, 열린 질문)
3. 명령 작성         docs/runs/<id>.md = 작업 본문 + "## 리뷰 포인트"
4. 명령 점검         Claude가 실행 전에 관련 코드와 대조한다(이름, 구조, 계산이 실제로 성립하는지)
5. 커밋             명령 파일을 run 전에 커밋한다(커밋하지 않으면 run의 diff에 섞인다)
6. run              jevcode run --tag <feature|fix|retry> --prompt-file docs/runs/<id>.md
7. 근거 모으기       시뮬레이터 출력, 리뷰 화면(공개 API, 삭제된 테스트, 기존 동작 변경), 근거 표, Play
8. 판정             사람이 먼저 정한다(블라인드). 체크리스트는 실제로 근거를 본 항목만 체크하고, 메모를 남긴다
9. 수락·커밋 또는 거절·되돌림   리뷰 화면에서
10. 기록            next-runs.md에 결과·Play 메모·비용, ai-design.md 단계 표, overview.md 다음 할 일
```

run이 도는 동안과 리뷰가 끝나기 전에는 Claude가 저장소 문서를 고치지 않는다. 고치면 그 run의 diff에 섞인다.

## 지켜 온 원칙

**명령 쓰기** (`behind-the-curtain/docs/next-runs.md` "명령을 쓰는 원칙"에 원문)

- 용어는 계산식으로, 수치는 설정으로, 기본값은 명령에 적는다.
- **테스트에는 불변식만 둔다**(금지 패턴, 결정론, 행동 정의의 경계). 실행해 보지 않은 분포 숫자(점유율, 몰림 비율)는 보고로 받고 사람이 판단한다.
- **극단값(100%, 0, 0.00)은 지표부터 의심한다.** 다른 근거(대상 고정, 실제 이동 거리)로 순환이 아닌지 확인한다.
- 행동을 바꾸는 run은 궤적 해시 갱신을 허락하되, 바뀐 시나리오마다 이유와 전후 지표를 적게 한다. 바뀌면 안 되는 시나리오는 "해시 갱신 없이 통과"를 요구한다.
- 범위를 작게 나눈다. 큰 run은 한도와 리뷰 부담이 크고, 실패하면 원인을 가리기 어렵다.
- 마지막 메시지에 '검증 근거' 표를 요구한다. 보고는 한국어로(`AGENTS.md`).

**리뷰 포인트 쓰기**

- 형식: `- [어디서] 무엇을 하면 → 무엇이 보이면 통과`. 어디서 = 리뷰 화면 / 근거 표 / 시뮬레이터 / 터미널 / Play. 명령은 그대로 붙여 넣을 수 있게(리뷰 화면에 복사 버튼이 생긴다).
- 그 run 시점에 확인할 수 있는 것만. Play는 바뀐 동작이 Unity에 연결돼 있을 때만.
- 코드를 읽어야 판단하는 항목은 넣지 않는다. 대신 그걸 검사하는 테스트를 요구하고, 테스트 이름을 근거 표와 리뷰 화면에서 대조한다.

**판정**

- 잣대: 살려서 고칠 결과면 수락, 버리고 다시 돌릴 결과면 거절.
- 거절 원인이 명령(Claude의 설계)에 있으면 "따로 볼 run"으로 기록한다(에이전트 품질 라벨이 아니므로).
- 사람이 먼저 판정하고, Claude의 의견은 그 뒤에 듣는다.

**저장소**

- 커밋은 `git status`로 확인한 뒤 명시적 경로로만. 푸시는 사람이 한다.
- jevcode의 A0 기록(`%LOCALAPPDATA%\JevCode\a0`)은 지우지 않는다.

## 배운 것

- **명령의 실수가 가장 큰 비용이었다.** 거절 2건(T16b-2f, 3a-1f)이 모두 명령 결함이었다: 순환 지표(힐러가 탱커 뒤로 줄을 서서 생긴 100%), 실행해 보지 않은 숫자를 테스트로 박음, 모순된 기준. 그 뒤로 명령을 실행 전에 코드와 대조한다(U7, 3a-1c, S1에서 실제로 문제를 찾아 고침). 3a-1d에서는 대조로 결함 다섯 개를 찾았다: 지금은 실행되지 않는 규칙을 "그대로 둔다"고 씀, 사람이 따라오면 끝없이 물러남, 천천히 다가오면 찌르지 않고 계속 물러남, 없앨 규칙을 검사하는 기존 테스트, 기본값에서 또 0이 나올 지표. 수락됐다.
- **테스트를 통과시키려다 설계가 깨질 수 있다.** 3a-1r에서 무반응 금지 패턴을 통과시키려고 들어간 규칙이 견제의 물러남을 없앴고, 리뷰에서 놓쳤다. Play 메모가 잡았다.
- **지표에는 빈틈이 있다.** 끊김 지표가 공격 정지를 정상으로 빼서 "서 있기만 한다"를 못 잡았다. 반응 지연 하나는 모든 조합에서 0이었다. 지표는 Play와 함께 본다.
- **Play 메모가 가장 정확한 신호였다.** "원패턴", "멀뚱멀뚱", "떤다", "물러나지 않는다"는 모두 Play에서 먼저 나왔다.
- **run을 작게 나누면 싸다.** 시뮬레이터나 Unity 연결만 하는 run은 30만~70만 토큰, 행동 여러 개를 한 번에 넣은 run은 350만~400만 토큰이었다.
