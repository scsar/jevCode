## 왜 하는가

- **에이전트 코딩을 감으로 쓰지 않기 위해.** 무엇을 시켰고, 무엇이 바뀌었고, 검증은 통과했는지, 사람이 왜 수락·거절했는지를 run 단위로 남긴다. 나중에 "그때 왜 이렇게 됐지"를 기록만으로 설명할 수 있어야 한다.
- **판단 모델이 진짜 쓸모 있는지 확인하기 위해.** Jev는 텍스트를 쓰지 않고 확률과 점수만 돌려주는 모델이다. 이 판단을 **사람 라벨과 블라인드로 비교**해 채점한다. **API가 사라져도 이 검증 방법 자체는 유효해야 한다**는 것이 처음부터의 전제다.
- **안전하게.** 에이전트는 OS 샌드박스 안에서만 돌고, `.git`은 쓰기 금지이며, 커밋과 푸시는 사람이 한다.
- **게임을 실제로 만들기 위해.** 검증만을 위한 장난감 과제가 아니라, 재미를 판단해야 하는 진짜 작업이라야 데이터에 의미가 있다.

## A0 진행 원칙 (2026-09-23 정리)

운영 지침이다. 판정 기준(설계 문서 10.2)은 바꾸지 않는다.

**어디까지 하나**

- **멈추는 기준은 날짜다.** 10-05에 끝낸다. 중간 결과를 보고 기간, 판정 기준, 질문 세트를 바꾸지 않는다.
- **건수는 거절 수로 본다.** E2·E3의 신호는 거절 run에서 나온다. 따로 볼 run을 빼고 거절 20~30건이면 방향성은 말할 수 있다(지금 거절률이면 run 80~100건).
- **`verificationStatus=skipped` run을 챙긴다.** 규칙 기준선이 약한 구간이라 Jev의 가치가 드러날 가능성이 가장 크다. Unity 작업이 자연스럽게 섞이게 한다. 일부러 만들지는 않는다.
- **현재 흐름이면 "효과 불명"일 가능성이 크다.** 판정은 E1이 필수인데, 지금 Brier는 규칙 0.101, Jev 0.141이다. 그렇게 나오면 우선순위 신호(E2)와 함께 그대로 기록하고 v0.6이나 질문 세트 v2의 근거로 쓴다.
- 10-05에 거절 수가 크게 모자라면 기간을 늘리지 않고 "표본 부족"으로 기록한다.

**하지 않는다**

- 건수를 채우려고 장난감 과제를 넣는 것.
- 피곤할 때 리뷰를 몰아서 대충 하는 것. 라벨 품질이 건수보다 중요하다.
- A0 도중 Jev 점수를 보고 명령 작성 방식을 바꾸는 것.

**유효한 리뷰**

에이전트가 받은 명령에 대해 낸 결과물을 사람이 직접 보고, 고정된 잣대로 판정한 것.

1. **블라인드.** 판정 전에 Jev·rules의 답을 보지 않는다.
2. **결과물을 실제로 본다.** 최소한 diff를 읽는다. Unity 작업은 Play로 확인한다. "검증 통과했으니 수락"은 리뷰가 아니다.
3. **잣대는 하나.** 살려서 고칠 결과면 수락, 버리고 다시 돌릴 결과면 거절. 피곤해서, 다음 작업이 급해서 수락하지 않는다.
4. **에이전트 품질을 반영한다.** 도구 결함, 잘못 붙여 넣은 명령, run 도중 사람의 커밋이 원인이면 라벨은 남기되 따로 볼 run으로 표시한다.
5. **리뷰 시점에 고정한다.** 나중에 버그를 찾아도 라벨을 바꾸지 않는다. 그런 경우는 "꼼꼼 필요" 추정(이후 `fix` run이 같은 파일을 다시 고침)이 잡는다.
6. **원인은 가장 큰 이유 하나.**

**특히 조심할 것**

- **검증 결과를 따라 수락하는 습관.** 라벨이 rules의 입력(검증 결과)을 따라가면 rules의 Brier가 인위적으로 좋아지고 E1이 Jev에게 불공정해진다. 테스트가 있는 코어 작업일수록 diff를 직접 읽었는지 확인한다.
- **대화에서 보조 에이전트와 같이 리뷰하는 것.** 라벨에 다른 판단이 섞인다. 무효는 아니지만, 의견을 듣기 전에 먼저 수락·거절을 정하고, 대화에서 리뷰한 run은 표시한다(리뷰 시간 신호도 빠진다).

**자기 점검:** 다음 주에 이 run을 다시 봤을 때, 기록만으로 왜 수락·거절했는지 설명할 수 있는가. 예라면 유효한 리뷰다(E4의 "기록만으로 설명 가능"과 같은 기준).
